# 项目业务、安全与性能审计报告

> 审计时间：2026-09-23  
> 最近复核：2026-09-24  
> 审计范围：网关、认证、核心业务、搜索、AI、管理后台、数据库结构、前端请求链路、Docker 部署配置  
> 审计目标：识别业务一致性、信息安全、性能瓶颈、可扩展性和运维遗漏  
> 说明：本报告为审计结果，不包含本轮代码修改。

---

## 一、结论摘要

当前项目功能完整度已经较高，主要风险不在“功能是否能跑”，而集中在以下四类：

1. **服务信任边界**
   - 下游服务信任网关注入的 `X-User-Id` / `X-User-Role`。
   - 如果业务端口直接可达，可以绕过网关伪造身份。

2. **生产配置与密钥安全**
   - JWT、MinIO、数据库存在默认密钥或默认密码。
   - 部分后台和演示能力存在默认账号、默认密码。

3. **高频链路可扩展性**
   - 收藏列表存在全量内存分页。
   - 评论预览存在全量回复加载。
   - ES 每次写入强刷新。
   - 详情浏览量使用数据库单行自增。

4. **工程化和可观测性**
   - 缺少版本化数据库迁移。
   - 缺少统一 traceId、慢查询、缓存命中率、MQ 积压等指标。
   - 缺少越权、SSRF、重复提交和并发场景测试。

建议先处理 P0 安全问题，再处理 P1 性能问题，最后补 P2 工程化能力。

## 三、P0：安全与信任边界

### 3.1 下游服务信任网关请求头

**状态：已解决。业务端口默认绑定本机，网关身份签名和下游校验已实现。**

#### 现状

网关完成 JWT 校验后，将用户身份写入：

```text
X-User-Id
X-User-Role
```

业务服务不重新解析 JWT，而是直接信任这两个请求头：

```text
backend/inspire-gateway/src/main/java/com/inspire/platform/gateway/filter/JwtAuthGlobalFilter.java
backend/inspire-common/src/main/java/com/inspire/platform/common/interceptor/UserContextInterceptor.java
```

#### 风险

如果以下端口对公网、局域网或攻击者可达：

```text
inspire-auth    8081
inspire-core    8083
inspire-admin   8085
```

攻击者可以绕过网关，直接请求业务服务，并伪造：

```http
X-User-Id: 100000000000000001
X-User-Role: admin
```

可能导致：

- 越权读取或修改他人灵感。
- 删除他人评论、私信、收藏。
- 调用管理接口。
- 伪造点赞、收藏、关注、评论。

#### 当前部署风险

`docker-compose.yml` 默认将多个业务端口映射到宿主机：

```text
8081, 8082, 8083, 8085
```

如果生产防火墙没有明确阻止，这些端口会暴露在服务器 IP 上。

#### 修复方案

优先级最高，建议组合处理：

1. 生产环境只暴露网关：
   ```text
   80 / 443
   ```
2. 业务服务只加入 Docker 内部网络：
   ```text
   expose
   ```
   而不是：
   ```text
   ports
   ```
3. 网关转发前强制覆盖用户身份头，避免外部同名头被透传。
4. 内部服务增加第二层签名：
   - 网关使用内部密钥生成短时签名。
   - 业务服务验证签名后才信任 `X-User-Id`。
5. 对 `X-User-Id` 格式、来源 IP、内部签名做启动和请求级别校验。

#### 验收标准

- 从公网访问 `8081/8083/8085` 返回连接失败。
- 直接向业务服务发送伪造 `X-User-Id` 无法访问私有接口。
- 网关是唯一能设置用户上下文头的入口。

### 3.2 默认密钥和默认密码

**状态：部分解决。当前配置已移除明文默认值，但历史泄露值必须轮换并清理 Git 历史。**

#### 现状

以下位置存在默认值：

```text
docker-compose.yml
backend/inspire-core/src/main/resources/application.yml
backend/inspire-admin/src/main/resources/application.yml
```

主要风险项：

- JWT 密钥存在默认 Base64 值。
- MinIO 默认账号密码。
- 数据库默认密码。
- 演示 admin 默认密码。
- 管理后台存在固定初始密码。

#### 风险

如果生产误用默认配置，攻击者可以：

- 伪造或自行签发 JWT。
- 访问 MinIO。
- 访问 MySQL。
- 登录管理后台。
- 读取或覆盖业务数据。

#### 修复方案

1. 生产环境全部通过 Secret 管理工具注入：
   ```text
   Kubernetes Secret
   Docker Secret
   Vault
   云厂商密钥管理
   ```
2. 删除生产配置中的默认密钥值。
3. 启动时增加配置安全检查：
   - 如果 JWT 还是默认值，拒绝启动。
   - 如果 MinIO/MySQL 还是默认值，拒绝启动或只允许 dev profile。
4. 演示种子只能在显式环境变量下运行：
   ```text
   INSPIRE_DEMO_SEED=true
   ```
5. 生产构建中禁止自动创建 admin。
6. 管理后台首次登录强制改密码。

#### 验收标准

- 生产启动时没有显式密钥会失败。
- 日志、配置、镜像中不存在真实密钥。
- 演示种子不会在生产 profile 下执行。

### 3.3 远程 URL 上传存在 SSRF 风险

**状态：已解决。远程 URL 使用域名白名单、公网 IP 校验、禁止重定向和下载大小限制。**

#### 现状

接口：

```text
POST /api/file/upload-from-url
```

实现位置：

```text
backend/inspire-core/src/main/java/com/inspire/platform/core/controller/FileController.java
```

当前实现允许服务端根据客户端提供的外部 URL 下载图片。

同时代码中存在信任所有证书的 HTTPS 客户端：

```java
TrustManager[] trustAll
```

#### 风险

攻击者可能提交：

```text
http://127.0.0.1:8080/...
http://169.254.169.254/...
http://内网服务地址/...
```

诱导服务器请求内网资源，造成：

- 内网端口探测。
- 云元数据读取。
- 访问内部管理接口。
- 通过重定向绕过域名限制。
- 下载超大文件导致内存或磁盘耗尽。

信任所有证书还会失去 HTTPS 身份校验。

#### 修复方案

1. 建立允许下载的域名白名单。
2. 禁止以下协议：
   ```text
   file
   ftp
   gopher
   data
   ```
3. DNS 解析后检查目标 IP：
   - 禁止私网地址。
   - 禁止回环地址。
   - 禁止链路本地地址。
   - 禁止云元数据地址。
4. 禁止自动跟随重定向，或每次跳转都重新校验。
5. 限制下载大小、超时时间和并发数。
6. 生产环境移除 trust-all SSL。
7. 如只服务 Unsplash、Picsum 等已知来源，直接使用固定域名白名单。

#### 验收标准

- 请求 `127.0.0.1`、内网网段、云元数据地址全部被拒绝。
- 302 跳转到内网地址被拒绝。
- 超大文件被中断。
- 生产环境不会关闭证书校验。

### 3.4 登录风控不足

**状态：已解决。IP 限流之外，账号级失败计数、验证码、临时锁定与管理员 TOTP MFA 已接入。**

#### 现状

网关已有 IP 级别限流：

```text
inspire-auth rate limiter
```

但当前阈值偏宽，主要限制整体请求量，不等于账号级登录保护。

#### 风险

- 撞库。
- 弱密码爆破。
- 多 IP 分布式尝试。
- 管理员账号被暴力猜测。

#### 修复方案

1. 增加账号维度失败计数：
   ```text
   login_fail:{username}
   ```
2. 连续失败后：
   - 增加验证码。
   - 短时锁定。
   - 发送安全通知。
3. 管理后台增加 MFA。
4. 新设备登录增加二次验证。
5. 记录异常登录：
   - IP。
   - 设备。
   - 地理位置。
   - 时间。
6. 注册、找回密码也增加更严格的限流和验证码。

#### 验收标准

- 单账号短时间多次失败会被限制。
- 分布式 IP 爆破也不会绕过账号级限制。
- 管理员登录具备额外验证。

### 3.5 前端硬编码长登录账号

**状态：已解决。前端硬编码账号白名单已删除，后端通过 `longLived` 返回会话策略。**

#### 现状

前端存在硬编码长登录账号：

```text
frontend/src/utils/tokenStorage.js
```

```js
const LONG_LIVED_ACCOUNTS = new Set(['user001', 'user002', 'user003', 'admin'])
```

#### 风险

- 暴露可尝试的账号范围。
- 前端策略可以被修改。
- 前端无法决定真实安全边界。
- 如果账户名为敏感信息，会形成信息泄露。

#### 修复方案

1. 删除前端账号白名单。
2. 长登录策略只由后端决定。
3. 后端按用户角色、设备、风险等级下发 token TTL。
4. 前端只根据 token 的有效期和刷新结果处理会话。

#### 验收标准

- 前端源码中不再出现固定用户账号。
- 修改本地 JavaScript 无法延长服务端 token 有效期。

## 四、P1：性能与可扩展性

### 4.1 收藏列表全量加载后内存分页

**状态：已解决。v2 已改为数据库分页。**

#### 现状

```text
InspireServiceImpl.listMyCollects()
```

逻辑：

1. 查出用户全部收藏。
2. Java 内存中计算总数。
3. Java 内存中 `subList`。

#### 风险

用户收藏达到数万条后：

- 数据库返回大量 ID。
- JVM 内存占用增加。
- 请求响应变慢。
- 并发用户多时容易抖动。

#### 修复方案

改为数据库分页：

```sql
SELECT ...
FROM collect_N
WHERE user_id = ?
ORDER BY create_time DESC
LIMIT ? OFFSET ?
```

更推荐游标分页：

```text
create_time + inspire_id
```

#### 验收标准

- 分页只读取当前页数据。
- 收藏量从 1 万增长到 100 万时，首响应时间不明显增长。

### 4.2 评论预览加载全部回复

**状态：已解决。仅允许发送后 2 分钟内撤回，并记录撤回人和原内容摘要。**

#### 现状

```text
CommentServiceImpl.listByInspireId()
```

每个主评论只展示 3 条回复预览，但数据库查询会先取出主评论下的全部回复，再在 Java 中截断。

#### 风险

热门评论有数百条回复时：

- 数据库返回大量无用记录。
- 网络传输浪费。
- 序列化和排序浪费。

#### 修复方案

为每个主评论单独取前 3 条：

```text
窗口函数
```

或：

```text
批量查询 + 每组 LIMIT 3
```

#### 验收标准

- 主评论接口返回条数与查询数据量接近。
- 回复总数不再依赖全量回复加载。

### 4.3 ES 每次 bulk 都刷新

**状态：未解决。**

#### 现状

```text
EsSyncService.bulkWrite()
```

批量写入使用：

```text
/_bulk?refresh=true
```

#### 风险

每次写入都触发 ES 刷新，导致：

- 写放大。
- segment 增多。
- 搜索延迟和索引性能下降。

#### 修复方案

1. 写入改为：
   ```text
   refresh=false
   ```
2. 使用定时 refresh：
   ```text
   每秒 / 每几秒
   ```
3. 对搜索一致性要求较低的场景容忍短暂延迟。

#### 验收标准

- 高频写入时 ES CPU 和 segment 增长明显降低。
- 搜索数据延迟在可接受范围内。

### 4.4 详情页浏览量单行自增

**状态：未解决。**

#### 现状

每次读取详情：

```sql
UPDATE inspire_main
SET view_count = view_count + 1
WHERE id = ?
```

#### 风险

热门文章会产生单行写热点，导致：

- 行锁竞争。
- MySQL 写入压力。
- 详情接口响应抖动。

#### 修复方案

1. Redis 计数器：
   ```text
   view:{inspireId}
   ```
2. 定时批量落库。
3. 页面缓存层定期聚合。
4. 详情接口先返回数据，异步记录浏览。

#### 验收标准

- 爆款文章高并发访问时，数据库没有明显行锁等待。
- 浏览量允许秒级最终一致。

### 4.5 缓存失效不完整

**状态：未解决。**

#### 现状

公开列表和推荐列表使用缓存，但发布、修改、删除后的失效策略需要进一步确认。

#### 风险

- 用户刚发布的灵感短时间不可见。
- 修改后的标题或封面在列表中仍是旧值。
- 删除后的内容可能短期仍出现。

#### 修复方案

明确缓存失效边界：

```text
发布 -> 清除公共列表
修改 -> 清除详情、列表、推荐
删除 -> 清除详情、列表、推荐、搜索结果
收藏/点赞 -> 只影响个性化状态，不失效公共内容
```

建议使用事件驱动缓存失效，避免写业务代码到处手动删除。

### 4.6 关注流 IN 查询扩展性不足

**状态：未解决。**

#### 现状

关注流使用：

```sql
user_id IN (关注列表)
ORDER BY create_time DESC
```

#### 风险

关注人数增长后：

- IN 列表变大。
- 排序成本变高。
- 索引选择性下降。

#### 修复方案

改为收件箱模型：

```text
发布灵感
→ 写入关注者 feed 表
→ 用户读取自己的 feed
```

同时增加清理策略，避免 feed 无限增长。

### 4.7 私信轮询压力

**状态：未解决。**

#### 现状

前端每 3 秒轮询：

- 会话列表。
- 当前消息。

#### 风险

## 五、P1：业务一致性

### 5.1 昵称 @ 可能重名

**状态：已解决。昵称已唯一，@关系内部使用用户ID。**

#### 现状

`@昵称` 通过昵称匹配用户。

#### 风险

两个用户昵称相同时，通知可能误发或发给多人。

#### 修复方案

1. 用户昵称增加唯一约束。
2. 候选列表内部保存 `userId`。

```text
comment_mention(
  comment_id,
  mentioned_user_id,
```

### 5.2 撤回规则缺少边界

**状态：未解决。**

#### 现状

私信撤回当前主要判断是否是发送者。

#### 风险

  ```text
  recalled_at
  recalled_by
  original_message_hash
  ```

### 5.3 通知指向已删除内容

**状态：已解决。目标灵感删除后关联通知会标记失效，列表也会返回目标可用状态。**

#### 现状

### 5.4 演示种子可能污染生产

**状态：未解决。**

#### 现状

`DemoDataSeeder` 可创建用户、灵感、评论、私信、通知和 admin。

#### 风险

如果生产误开：

```text
INSPIRE_DEMO_SEED=true
```

会生成大量虚拟数据，甚至创建默认账号。

#### 修复方案

1. 只在 `dev` 和显式开关同时满足时运行。
2. 生产 profile 下直接拒绝。
3. 种子生成使用独立数据库。
4. Admin 不允许由种子自动创建。
