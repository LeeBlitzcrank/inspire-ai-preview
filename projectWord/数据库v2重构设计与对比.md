# 数据库 v2 重构设计与对比

> 更新时间：2026-09-24
> 重构原则：不迁移旧数据，直接重建 v2 演示库
> 目标：解决业务一致性、跨分片查询、重复状态、索引不匹配、数据归档和迁移漂移问题

---

## 一、重构结论

数据库 v2 已完成落地。

核心变化：

- 手工维护的 40 张互动分表已移除。
- 收藏、点赞、评论、评论点赞改为 MySQL HASH 分区表。
- 消息未读状态只保留在成员表。
- 私信删除改为成员游标，不再依赖每条消息的双侧删除字段。
- @提及新增独立关系表，内部使用用户 ID。
- 通知增加目标类型、事件幂等键和已读时间。
- 评论字段从 `username` 明确改为昵称字段。
- 新增 Flyway 版本化迁移机制。

---

## 二、核心数据模型 v2

### 2.1 收藏

表：

```text
collect
```

关键字段：

```text
id
user_id
inspire_id
folder_id
create_time
```

分区：

```text
PARTITION BY HASH(user_id) PARTITIONS 32
```

关键索引：

```text
PRIMARY KEY(user_id,id)
UNIQUE(user_id,inspire_id)
INDEX(user_id,folder_id,create_time)
INDEX(user_id,create_time)
INDEX(inspire_id,user_id)
```

解决的旧问题：

- 不再维护 `collect_0 ~ collect_9`。
- “我的收藏”按用户维度只会命中一个分区。
- 收藏列表分页可以直接走数据库和 `(user_id, create_time)` 索引。

### 2.2 点赞

表：

```text
user_like
```

分区：

```text
PARTITION BY HASH(user_id) PARTITIONS 32
```

关键索引：

```text
PRIMARY KEY(user_id,id)
UNIQUE(user_id,inspire_id)
INDEX(inspire_id,user_id)
INDEX(user_id,create_time)
```

解决的旧问题：

- 不再维护 `user_like_0 ~ user_like_9`。
- “当前用户是否点过赞”只查询单个分区。
- 明细表和主表冗余计数可以逐步改为事件驱动更新与对账。

### 2.3 评论

表：

```text
inspire_comment
```

字段变化：

```text
username        -> author_nickname
reply_username -> reply_nickname
新增 root_id
```

分区：

```text
PARTITION BY HASH(inspire_id) PARTITIONS 32
```

关键索引：

```text
PRIMARY KEY(inspire_id,id)
INDEX(inspire_id,parent_id,deleted,like_count,create_time)
INDEX(inspire_id,parent_id,deleted,create_time)
INDEX(user_id,deleted,create_time)
```

解决的旧问题：

- 不再维护 `inspire_comment_0 ~ inspire_comment_9`。
- 详情页评论只命中一个分区。
- `author_nickname` 明确表示展示昵称，不再和登录账号混淆。
- `root_id` 支持后续更高效的两级折叠和回复统计。

### 2.4 @提及

表：

```text
comment_mention
```

字段：

```text
id
comment_id
inspire_id
mentioned_user_id
display_name
create_time
```

分区：

```text
PARTITION BY HASH(inspire_id) PARTITIONS 32
```

唯一键：

```text
UNIQUE(inspire_id,comment_id,mentioned_user_id)
```

解决的旧问题：

- 展示文本使用昵称。
- 通知和关系内部使用 `mentioned_user_id`。
- 昵称重名不会再导致错误通知多人。
- 删除评论时可以同步删除提及关系。

### 2.5 评论点赞

表：

```text
comment_like
```

字段：

```text
id
user_id
comment_id
inspire_id
create_time
```

分区：

```text
PARTITION BY HASH(user_id) PARTITIONS 32
```

关键索引：

```text
PRIMARY KEY(user_id,id)
UNIQUE(user_id,comment_id)
INDEX(comment_id,user_id)
INDEX(inspire_id,create_time)
```

解决的旧问题：

- 不再维护 `comment_like_0 ~ comment_like_9`。
- 当前用户点赞状态按用户分区读取。
- 冗余 `inspire_id` 方便内容删除和批量清理。

### 2.6 私信会话

`message_conversation` 现在只保存会话本身：

```text
id
user1_id
user2_id
last_message_id
last_content
last_time
create_time
update_time
```

已删除旧字段：

```text
unread_user1
unread_user2
```

未读状态只保留在：

```text
conversation_member
```

成员表新增：

```text
last_read_message_id
deleted_before_message_id
```

索引：

```text
INDEX(user_id,deleted,last_time)
```

解决的旧问题：

- 不再存在两套未读状态。
- 会话列表索引与查询条件一致。
- 删除会话变成“当前用户隐藏到某个消息游标之前”，不会影响对方。

### 2.7 私信消息

表：

```text
message
```

已删除：

```text
deleted_by_sender
deleted_by_receiver
```

分区：

```text
PARTITION BY HASH(conversation_id) PARTITIONS 32
```

主键：

```text
PRIMARY KEY(conversation_id,id)
```

读取消息时：

```text
conversation_id = ?
AND id > conversation_member.deleted_before_message_id
```

解决的旧问题：

- 删除会话不再逐条修改消息状态。
- 消息删除状态由成员游标统一控制。
- 会话消息读取可以稳定命中会话分区。

### 2.8 通知

表：

```text
user_notification
```

新增：

```text
target_type
event_key
read_time
```

`event_key` 唯一，防止事件重试时产生重复通知。

通知类型现在支持：

```text
like
collect
comment
reply
follow
mention
quote
special_publish
```

### 2.9 用户与昵称

`user` 新增唯一约束：

```text
UNIQUE(nickname)
```

注册和修改资料时增加昵称重复检查。

解决的问题：

- `@昵称` 不再有重名歧义。
- 展示昵称与登录账号彻底分离。

### 2.10 其他结构优化

`inspire_version`：

```text
INDEX(inspire_id,version_number DESC)
```

`sys_upload_image`：

```text
UNIQUE(file_key)
```

`password_reset`：

```text
UNIQUE(token)
```

`collect_folder`：

```text
UNIQUE(user_id,name)
```

## 三、v1 与 v2 对比

| 项目 | v1 | v2 |
| --- | --- | --- |
| 收藏 | `collect_0~9` 手工分表 | `collect` 32 分区 |
| 点赞 | `user_like_0~9` 手工分表 | `user_like` 32 分区 |
| 评论 | `inspire_comment_0~9` 手工分表 | `inspire_comment` 32 分区 |
| 评论点赞 | `comment_like_0~9` 手工分表 | `comment_like` 32 分区 |
| 分片路由 | Java ThreadLocal + 动态表名 | MySQL 分区裁剪 |
| 收藏分页 | 全量加载后内存分页 | 数据库分页 |
| 评论字段 | `username` 存昵称 | `author_nickname` |
| @提及 | 仅解析评论文本 | `comment_mention` 关系表 |
| 未读状态 | conversation + member 两套 | 仅 member |
| 会话删除 | 逐条消息标记或物理删除 | 成员删除游标 |
| 通知幂等 | 无 | `event_key UNIQUE` |
| 通知目标类型 | 无 | `target_type` |
| 已读时间 | 无 | `read_time` |
| 昵称唯一 | 无 | `UNIQUE(nickname)` |
| 迁移管理 | init.sql + ALTER | Flyway + `V1` baseline |
| 文档 | 与实际结构有漂移 | 本文件作为 v2 设计基准 |

```text

```

配置：

```text
flyway_schema_history_core

```

本地验证结果：

```text
版本 0：Flyway Baseline

```

```text

```

## 五、重构过程中出现的问题

### 问题 1：分区表唯一索引必须包含分区键

第一次建表时，`comment_mention` 使用：

```text
UNIQUE(comment_id,mentioned_user_id)
PARTITION BY HASH(inspire_id)
```

MySQL 拒绝创建，因为唯一索引不包含分区键。

修复为：

```text
UNIQUE(inspire_id,comment_id,mentioned_user_id)
```

同样规则适用于：

- `collect`
- `user_like`
- `inspire_comment`
- `comment_like`
- `message`

所有分区表的唯一键和主键均包含分区字段。

### 问题 2：应用层动态表名与 MySQL 分区冲突

v1 使用：

```text
DynamicTableNameInnerInterceptor
+ ShardContext
```

v2 已移除动态表名拦截器和 `ShardContext`，Mapper 直接访问统一逻辑表，由 MySQL 完成分区裁剪。

### 问题 3：消息未读状态双写

v1 中：

```text
message_conversation.unread_user1/unread_user2
conversation_member.unread_count
```

存在两套状态。

v2 只保留 `conversation_member.unread_count`，彻底消除漂移。

### 问题 4：私信删除导致对方数据受影响

v1 删除会话可能物理删除消息或影响双方。

v2 改为：

```text
conversation_member.deleted
conversation_member.deleted_before_message_id
```

每一边独立删除、独立恢复，不影响对方历史。

### 问题 5：@昵称重名

仅靠文本 `@昵称` 无法确保唯一。

v2：

- 昵称增加唯一约束。
- 新增 `comment_mention`。
- 通知通过 `mentioned_user_id` 发送。
- 昵称只承担展示职责。

### 问题 6：旧表名和字段名残留

重构时出现多处旧引用：

```text
collect_0
user_like_0
inspire_comment_0
comment_like_0
username
reply_username
deleted_by_sender
deleted_by_receiver
```

已全部清理，并通过全文检索确认没有残留。

### 问题 7：保留旧数据会影响重构

本次按你确认的方案不迁移旧数据，直接重建演示库。

这样做：

- 避免双写。
- 避免历史状态迁移。
- 避免旧分片数据清理成本。
- 让 v2 从第一天就是干净状态。

## 七、当前仍需后续处理

数据库 v2 解决了结构性设计问题，但以下事项仍建议后续继续推进：

1. 把点赞、收藏、评论数迁移到独立 `inspire_metric` 表，并由事件总线和定时对账维护。
2. 对通知、消息、Web Vitals、AI 日志增加定期归档任务。
3. 根据真实增长量评估 32 个分区是否足够，必要时迁移到 TiDB/Vitess。
4. 增加慢查询监控、分片命中统计和容量预警。
5. 把私信轮询改为 WebSocket/SSE。
6. 将后台管理、网关和业务服务之间的内部信任边界继续加固。

## 八、结论

v2 相比 v1 的主要收益：

- 表数量明显减少。
- 分区由数据库管理，不再手工路由。
- 高频用户维度查询可以稳定分区裁剪。
- 消息状态单一化。
- 评论昵称语义明确。
- @提及不再依赖重名文本。
- 通知具备幂等和类型信息。
- 数据库迁移进入可追踪模式。

当前 v2 已经可以支撑更大规模的用户互动数据，并为后续计数重构、归档和分布式扩展留出了清晰路径。

## 九、容量评估：万级还是千万级

数据库能否支撑某个规模，不能只看“表有多少行”，还要区分：

- 数据总量。
- 单表最大行数。
- 每秒写入量。
- 热点内容并发量。
- 单次查询返回量。
- 机器 CPU、内存、磁盘和连接数。
- 是否存在跨分片、全表扫描和大范围排序。

### 9.1 万级

```text
1 万 ~ 10 万级
```

结论：

```text
完全够用，而且有明显的结构冗余。
```

v2 的 32 分区在万级数据下不会带来正确性问题，但数据库分区元数据和维护复杂度会高于实际需要。这个阶段最重要的是：

- 保持代码正确。
- 监控慢查询。
- 确认索引真正命中。
- 尽量避免无索引排序。

### 9.2 十万级到百万级

```text
10 万 ~ 500 万级
```

结论：

```text
这是 v2 设计的舒适区。
```

原因：

- 收藏和点赞按 `user_id` 分区，用户维度查询只命中少量分区。
- 评论和消息按 `inspire_id` / `conversation_id` 分区，详情查询只命中单个分区。
- 分区表聚合索引减少跨分片查询。
- 通知、点赞、收藏、评论都具备清晰索引。
- Flyway 已接入，后续可以按版本稳定演进。

在中等配置 MySQL 上，百万级数据本身通常不是瓶颈。真正需要关注的是：

- 爆款内容的读并发。
- 计数字段的重复写入。
- ES 同步。
- 图片和视频流量。
- 列表接口是否分页。
- 是否存在 `SELECT *` 和无索引排序。

### 9.3 千万级

```text
1000 万 ~ 5000 万行
```

结论：

```text
有机会，但需要压测和调优，不能只靠当前表定义承诺。
```

需要区分两种情况：

1. **总数据量达到千万级**
   - 如果主要是冷数据、读多写少、查询都有索引，单 MySQL 加 32 个分区是有可能支撑的。
   - 前提是磁盘、内存、连接池和慢查询都调优过。

2. **每天新增千万级互动**
   - 单 MySQL 不适合。
   - 需要独立写入通道、异步聚合、消息队列、分区归档和横向扩容。

千万级下必须补的能力：

- 独立计数/聚合表。
- 事件 outbox 和异步消费。
- 热点计数放 Redis。
- 点赞、收藏、评论批量落库。
- 冷热数据分层。
- 分区归档和清理。
- 慢查询和 P95/P99 监控。
- 压测脚本覆盖真实查询路径。

### 9.4 一亿级以上

```text
1 亿 +
```

结论：

```text
不建议继续依赖单实例 MySQL 手工分区。
```

此阶段建议评估：

- TiDB。
- Vitess。
- 分库分表中间件。
- 读写分离加多分片。
- 冷热数据分离。
- ES/ClickHouse 等分析型存储。

这时数据库设计的重点会从“分区是否合理”转向：

- 分片键是否和业务路由一致。
- 跨分片查询是否被消除。
- 数据归档是否自动化。
- 计数是否最终一致。
- 故障恢复和扩容是否需要停机。

### 9.5 当前 v2 的明确结论

```text
万级：完全没有问题
十万级：舒适
百万级：设计目标区间
千万级：可支持，但必须经过调优和压测
一亿级：需要分布式数据库或正式分库分表
```

当前 v2 不是为了“单机无限扩展”，而是为了：

- 让百万级常见业务查询保持稳定。
- 消除手工分表维护成本。
- 为后续迁移到分布式方案提供更干净的数据模型。

## 十、后续扩展路线

### 10.1 第一层：计数与热数据分离

新增：

```text
inspire_metric
```

负责：

```text
view_count
like_count
collect_count
comment_count
heat
```

写入策略：

```text
Redis 实时计数
→ 消息队列或定时任务批量落库
→ 定时对账校准
```

### 10.2 第二层：事件 Outbox

新增：

```text
domain_event_outbox
```

业务写入和事件写入在同一事务中完成，再异步处理：

- 通知。
- ES 同步。
- 缓存失效。
- 关注流 fanout。
- 计数更新。

这样可以解决“主业务成功，但通知或搜索同步失败”的一致性问题。

### 10.3 第三层：热点内容缓存

Redis 缓存：

```text
inspire:detail:{id}
inspire:comments:first-page:{id}
user:profile:{id}
ranking:hot
```

要求：

- 设置短 TTL。
- 更新时主动失效。
- 热点内容走本地缓存加 Redis 两级缓存。

### 10.4 第四层：读写分离

读取流量按场景拆分：

```text
主库：写操作、强一致读
从库：列表、详情、评论、通知
Redis：热点计数和排行榜
ES：搜索
```

### 10.5 第五层：数据归档

需要归档的表：

```text
message
user_notification
web_vital_metric
ai_call_log
inspire_version
```

策略：

- 按月份分区。
- 在线保留最近 3～12 个月。
- 历史数据归档到冷存储。
- 后台按需查询归档数据。

### 10.6 第六层：分布式数据库

当单机成为瓶颈时：

```text
MySQL 单实例 + 分区
→ 读写分离
→ 多分片
→ TiDB / Vitess
```

迁移时优先保持：

- 逻辑表和业务 API 不变。
- 分区键和查询路径不变。
- 代码不直接依赖物理表名。

---

## 十一、最终判断

当前 v2 设计的目标范围是：

```text
真实业务：十万到百万级
经过调优：千万级
超过千万级：需要继续演进
```

它比 v1 更适合长期扩展，但不是“单实例可以无上限”的架构。后续只要按“计数分离 → Outbox → 缓存 → 读写分离 → 归档 → 分布式”的路线推进，可以在不重新推翻业务模型的情况下继续扩容。
