## 二、灵感标题 16 字限制

### 1. 统一规则

灵感标题最大长度统一为：

```text
16 个字符
```

该限制同时覆盖：

- 用户手动输入。
- 用户编辑已有灵感。
- AI 探索生成的标题。
- AI 多风格候选标题。
- 后端创建接口。
- 后端更新接口。
- 种子数据生成器。
- 历史数据的宽度清理。

### 2. 前端处理

文件：

```text
frontend/src/pages/Create.vue
```

已实现：

- 标题输入框增加 `maxlength="16"`。
- 输入框下方显示当前字数，例如 `12/16`。
- AI 内容返回后自动截断到 16 字。
- 切换 AI 文案风格时自动截断标题。
- 编辑已有灵感时自动截断历史标题。
- 提交前再次校验标题长度。

核心逻辑：

```js
const TITLE_MAX_LENGTH = 16
const titleLength = computed(() => Array.from(form.value.title || '').length)

const clampTitle = (value) =>
  Array.from(String(value || '')).slice(0, TITLE_MAX_LENGTH).join('')
```

使用 `Array.from()` 是为了按实际 Unicode 字符计数，避免直接依赖 JavaScript UTF-16 长度。

### 3. 后端统一规则

新增统一工具：

```text
backend/inspire-common/src/main/java/com/inspire/platform/common/util/TitleUtil.java
```

职责：

- 定义唯一标题上限 `MAX_LENGTH = 16`。
- 提供字符长度计算。
- 提供安全截断。
- 保留 Unicode 完整字符，不截断半个字符。

核心接口：

```java
public static final int MAX_LENGTH = 16;

public static int length(String value);

public static String truncate(String value);
```

## 三、评论区回复后立即展示

### 1. 问题现象

用户在灵感详情页回复某条评论后：

- 后端提示回复成功。
- MySQL 中确实已经生成回复记录。
- 当前页面评论区看不到刚发的回复。
- 刷新页面后也不一定立即看到。

### 2. 根因

评论列表默认按热度排序，并且每次只请求前 20 条全局评论记录。

新回复的初始点赞数为：

```text
0
```

因此新回复通常不在第一页。

旧逻辑在回复成功后执行：

```js
await loadComments(true)
```

它只重新拉取按热度排序的第一页，新回复仍然会被分页排除，所以页面无法显示。

该问题不仅影响回复，也会影响默认按热度查看时新发布的顶层评论。

### 3. 后端修复

文件：

```text
backend/inspire-core/src/main/java/com/inspire/platform/core/controller/CommentController.java
backend/inspire-core/src/main/java/com/inspire/platform/core/service/CommentService.java
backend/inspire-core/src/main/java/com/inspire/platform/core/service/impl/CommentServiceImpl.java
```

创建评论接口由原来的：

```java
Result<Void>
```

改为返回新创建的评论：

```java
Result<CommentVO>
```

接口：

```text
POST /api/inspire/{inspireId}/comment
```

成功返回示例：

```json
{
  "code": 200,
  "msg": "评论成功",
  "data": {
    "id": "228284058356944897",
    "userId": "100000000000000001",
    "username": "温暖小兔",
    "nickname": "温暖小兔",
    "content": "测试回复",
    "parentId": "100000000000704281",
    "likeCount": 0,
    "liked": false,
    "createTime": "2026-09-23T06:39:20"
  }
}
```

### 4. 前端修复

文件：

```text
frontend/src/pages/InspireDetail.vue
```

新增两个处理函数：

```js
const mergeCreatedComment = (created) => {
  // 将服务端返回的新评论直接合并到当前已加载列表。
}

const focusCreatedComment = async (created, root) => {
  // 展开对应回复并滚动到刚发布的内容。
}
```

回复成功后不再只依赖重新加载第一页，而是：

1. 使用创建接口返回的 `CommentVO`。
2. 合并到当前评论记录集合。
3. 更新评论总数。
4. 重新按当前排序规则分组。
5. 自动展开对应评论的回复区域。
6. 滚动到刚发布的回复。

快速发表顶层评论也使用同一套逻辑。

### 5. 二次进入修复

只做前端即时插入还不够，因为用户离开详情页再进入时，页面会重新请求评论列表。

评论列表分页已从：

```text
全局评论记录分页
```

改为：

```text
先按主评论分页，再一次性返回这些主评论下的回复
```

每页处理过程：

1. 按热度或时间查询当前页主评论。
2. 收集当前页的主评论 ID。
3. 一次查询这些主评论下的全部回复。
4. 将主评论和回复合并后返回。

这样二次进入热门主评论页时，该主评论下的回复会一起返回，不再依赖新回复是否进入全局前 20 条。

查询次数固定为：

```text
主评论分页查询 1 次
回复批量查询 1 次
评论总数查询 1 次
```

没有按每条主评论逐条查询，避免 N+1。

### 6. 性能考虑

该修复没有改成一次性加载全部评论，也没有取消分页。

实际策略是：

- 评论列表按主评论继续分页。
- 每页只加载当前主评论需要的回复。
- 新评论只增量合并一条服务端返回记录。
- 回复查询使用 `parent_id IN (...)` 批量读取。
- 不为了显示一条新回复扫描全部评论分表。
- 不改变评论按 `inspire_id % 10` 的分片规则。
- 不增加新的高频查询。

因此修复即时展示问题的同时，保留了原有评论分页性能。

## 四、AI 探索

### 1. 分层探索

AI 探索按路径逐层深入：

- 当前没有选择路径时，返回 3～5 个探索方向。
- 用户继续点击方向后，将路径传给后端。
- 路径深度达到最终内容时，返回完整灵感正文，不再返回子选项。

请求参数示例：

```json
{
  "keyword": "小户型收纳",
  "path": "storage,tool",
  "variants": 3
}
```

`variants` 默认为 3，后端限制在 1～5 组。

### 2. 多风格候选

一次最终内容生成会返回多组不同风格文案：

```json
{
  "style": "温柔治愈",
  "title": "收纳后的松弛感",
  "text": "300~500 字正文"
}
```

前端在创建页展示风格切换条，点击后直接替换标题和正文，不会把多组文案叠加在一起。

每组正文要求：

- 300～500 个中文字符。
- 3～5 个自然段。
- 至少有一段使用 `1. 2. 3.` 列出可执行建议。
- 整体内容具体，避免空泛。

### 3. Redis 全局缓存

AI 探索结果写入 Redis：

```text
ai:explore:v3:{keyword}|{path}
```

缓存规则：

- 有效期 24 小时。
- 同一关键词和路径可被其他用户复用。
- 命中缓存时不消耗模型 token。
- 点击「换一批」时先删除当前缓存，再重新请求模型。
- 返回字段 `fromCache` 标识本次是否命中缓存。

### 4. 用户探索历史

数据库表：

```text
user_ai_history
```

主要字段：

```sql
id
user_id
keyword
path
cache_key
result_json
selected_index
selected_title
status
create_time
update_time
deleted
```

索引：

```sql
KEY idx_user_ai_history (user_id, deleted, create_time)
KEY idx_cache_key (cache_key)
```

前端能力：

- 创建页展示「最近探索」。
- 默认加载最近 20 条。
- 点击历史记录后恢复关键词、路径、摘要、多风格候选、标题和正文。
- 切换风格时记录当前选择的 `selectedIndex` 和 `selectedTitle`。
- 用户可以删除自己的探索记录。

接口：

```text
GET    /api/inspire/ai/history?limit=20
POST   /api/inspire/ai/history
PUT    /api/inspire/ai/history/{id}/select
DELETE /api/inspire/ai/history/{id}
```

历史记录只对已登录用户开放，并且按用户隔离。

### 5. 性能策略

- Redis 全局缓存优先，避免相同探索重复调用模型。
- 一次生成多组风格，避免用户为同一主题重复请求。
- 历史列表默认限制 20 条，服务端最多允许 50 条。
- 历史结果按 JSON 存储，恢复时不需要再次调用模型。
- 不把模型结果长期塞进浏览器本地缓存，避免多设备不一致。

## 五、图片与视频上传

### 1. 前端上传流程

创建页一次最多选择 9 个文件。

图片流程：

1. 选择文件后立即生成本地预览。
2. 前端将最大边压缩到 1920。
3. 输出 JPEG，质量 0.85。
4. 使用 `onUploadProgress` 显示单张上传进度。
5. 上传成功后用服务端 URL 替换本地预览地址。

GIF 不经过前端 Canvas 压缩，避免破坏动画。

视频流程：

1. 视频单文件最大 50MB。
2. 立即生成本地预览。
3. 每个视频显示文件名、大小、上传百分比和状态。
4. 上传成功后替换为服务端地址，并记录视频时长。
5. 失败后保留原文件，可以点击「重新上传」。

当前已经实现的是上传进度和失败重试。

当前没有实现真正的分片上传、断点续传和服务端秒传。

### 2. 批量上传

多文件选择后使用 `Promise.all()` 并发上传：

- 图片和视频分别走各自上传分支。
- 单张图片显示独立进度。
- 页面顶部汇总平均上传进度。
- 超过 9 个时自动忽略超出部分并提示。
- 仍有文件上传时，阻止提交灵感。

### 3. 服务端图片处理

接口：

```text
POST /api/file/upload
```

服务端处理：

- 图片最大宽度超过 1920 时重新缩放。
- PNG 保留透明通道。
- 其他图片统一输出 JPEG。
- 生成传统缩略图。
- 生成 200 / 400 / 800 三档 WebP。

WebP 文件命名：

```text
{base}_w200.webp
{base}_w400.webp
{base}_w800.webp
```

上传响应包含：

```json
{
  "url": "/uploads/{base}_w800.webp",
  "thumbUrl": "/uploads/{base}_w400.webp",
  "url200": "/uploads/{base}_w200.webp",
  "url400": "/uploads/{base}_w400.webp",
  "url800": "/uploads/{base}_w800.webp"
}
```

列表优先使用 400 或 800 WebP，避免直接加载原图。

### 4. WebP 生成服务

文件：

```text
backend/inspire-core/src/main/java/com/inspire/platform/core/service/ImageVariantService.java
```

能力：

- 调用 ffmpeg `libwebp` 生成 WebP。
- 宽高按比例缩放，不拉伸。
- 输出质量 78。
- 支持本地文件和 MinIO。
- MinIO 已存在变体时只做 stat，不重复编码。

### 5. 视频上传

视频上传支持：

- MP4。
- WebM。
- MOV。
- M4V。

服务端校验：

- 文件大小不能超过 50MB。
- MIME 类型校验。
- 文件头魔数校验。
- 不做自动转码，保留原始画质。
- 尝试使用 ffmpeg 截取首帧作为封面。

上传完成后，用户可以按需执行：

- 视频压缩。
- 视频裁剪。
- 只保留最终处理版本。

### 6. AI 配图入库

AI 配图推荐返回的是站外 URL。

用户选中后，前端调用：

```text
POST /api/file/upload-from-url
```

服务端下载图片到本站存储，再返回本站地址，避免：

- 原图源 403。
- 跨域问题。
- 外链失效。
- 海报 Canvas 被污染。

WebP 原图保持 WebP 地址，不再用 Java ImageIO 强行解码重绘。

## 六、海报分享

### 1. 用户操作流程

详情页点击分享后：

1. 打开分享面板。
2. 可以复制详情链接。
3. 可以点击「生成分享海报」。
4. 进入模板选择面板。
5. 选择模板后生成 Canvas 预览。
6. 可以保存 PNG。
7. 可以重新选择模板。

### 2. 三套模板

当前模板：

| ID | 名称 | 主要特征 |
| --- | --- | --- |
| `paper` | 文艺纸感 | 纸张底色、细边框、衬线排版 |
| `minimal` | 极简留白 | 白底、大留白、简洁图片框 |
| `magazine` | 杂志封面 | 全图背景、深色渐变、杂志标签 |

默认模板是 `paper`。

### 3. 二维码

海报二维码在用户选择模板后才生成。

二维码内容：

```text
{当前站点域名}/#/detail/{灵感ID}
```

实现方式：

- 动态加载 `qrcode`。
- 使用 `QRCode.toDataURL()` 生成二维码。
- 绘制进 Canvas。
- 输出 PNG。

动态加载是为了避免进入详情页时就加载二维码库，减少首屏包体积。

### 4. 封面代理

站外图片可能需要跨域头才能绘制进 Canvas。

海报封面加载顺序：

1. 站内图片直接加载。
2. 站外图片优先请求 `/api/file/poster-cover`。
3. 代理失败时回退直连。

代理接口：

```text
GET /api/file/poster-cover?url={encodedUrl}
```

代理只允许白名单图源，并返回带 CORS 头的图片字节流。

### 5. 导出与防污染

- 海报尺寸使用统一逻辑画布常量。
- 图片使用等比裁切，不拉伸。
- Canvas 通过 `toDataURL('image/png')` 导出。
- 如果画布被跨域图片污染，会给出明确失败提示，不静默生成空白海报。
- 保存文件名使用 `inspire-{id}.png`。

### 6. 分享计数

已登录用户打开分享时调用：

```text
POST /api/inspire/{id}/share
```

后端使用原子 SQL 增加：

```sql
share_count = COALESCE(share_count, 0) + 1
```

游客可以打开分享面板，但不会调用需要登录的分享计数接口。

## 七、回复叠楼与折叠

### 1. 当前展示结构

评论区采用两级展示：

```text
主评论
  ├─ 回复 A
  ├─ 回复 B
  └─ 回复 C
```

即使种子数据里存在多层回复链，前端也会解析并归到同一个主评论下展示。

这样做的目的：

- 避免手机端无限缩进。
- 保持评论列表容易滚动。
- 保持每个主评论的回复折叠状态稳定。

### 2. 回复目标

回复主评论时：

- `parentId` 为主评论 ID。
- `replyUserId` 默认是主评论作者。

回复某条回复时：

- 数据仍然挂到主评论下。
- `replyUserId` 和 `replyUsername` 记录被回复的人。
- 展示时在正文前显示 `@被回复人`。

核心字段：

```sql
parent_id
reply_user_id
reply_username
```

### 3. 折叠规则

默认状态：

- 主评论显示在列表中。
- 回复默认收起。

展开后：

- 首次显示前 3 条回复。
- 点击「继续显示」每次增加 3 条。
- 可以点击「收起回复」恢复折叠。

相关前端状态：

```js
_repliesExpanded
_visibleReplyCount
```

这些状态只保存在当前页面内，不写数据库。

### 4. 回复提交后的即时展示

回复创建成功后：

1. 服务端返回完整评论记录。
2. 前端插入当前评论列表。
3. 自动展开该主评论的回复区。
4. 调整可见回复数量，确保新回复不会被折叠隐藏。
5. 自动滚动到刚发布的回复。

该逻辑解决“回复成功但第一页看不到”的分页问题。

### 5. 评论总数规则

评论区的“共 X 条评论”只统计主评论：

```text
parent_id = 0
```

回复不计入评论总数。

例如：

```text
1 条主评论
1 条回复
```

页面显示：

```text
共 1 条评论
```

前端“已显示”数量也只统计当前已经加载的主评论数量。

回复数量仍然会显示在对应主评论的展开区域中，例如：

```text
展开 1 条回复
```

### 6. 长评论性能

主评论容器使用：

```css
content-visibility: auto;
contain-intrinsic-size: auto 130px;
```

浏览器可以跳过屏幕外评论的布局和绘制，200+ 条评论时滚动更稳定。

### 7. 种子评论

种子数据会生成：

- 不同点赞量的主评论。
- 不同点赞量的回复。
- 带 `replyUserId` / `replyUsername` 的互相回复。
- 重点灵感约 200～300 条评论。

种子回复会挂到主评论下，并保留被回复用户信息。

### 4. 数据模型

收藏记录按 `user_id % 10` 分片：

```text
collect_0
collect_1
collect_2
collect_3
collect_4
collect_5
collect_6
collect_7
collect_8
collect_9
```

收藏记录唯一约束：

```sql
UNIQUE KEY uk_user_inspire (user_id, inspire_id)
```

含义：

- 同一用户对同一灵感只能保留一条有效收藏记录。
- 重复收藏不会生成重复数据。
- 已经收藏的内容可以移动到其他收藏夹。

收藏记录中的 `folder_id`：

- 有值：属于指定收藏夹。
- 为空：属于未分类收藏。

收藏夹表：

```text
collect_folder
```

收藏夹按用户隔离，用户只能查询、修改和删除自己的收藏夹。

### 5. 接口

收藏夹接口：

```text
POST   /api/inspire/collect/folder
GET    /api/inspire/collect/folders
PUT    /api/inspire/collect/folder/{id}
DELETE /api/inspire/collect/folder/{id}
```

收藏内容接口：

```text
POST /api/inspire/collect/{inspireId}/folder
PUT  /api/inspire/collect/{inspireId}/move
GET  /api/inspire/collect/list
```

### 6. 成功后的页面状态

统一组件在收藏成功后触发：

```text
collected
```

父页面收到事件后负责更新自己的状态：

- 首页：翻到下一张推荐卡。
- 搜索页：将收藏图标改为实心白色。
- 详情页：将收藏按钮改为选中状态，并增加收藏数量。

收藏组件本身不直接修改父页面数据，避免组件和页面状态互相侵入。

### 7. 性能考虑

- 收藏夹列表只在弹窗打开时加载。
- 收藏结果使用 `user_id` 分片，避免跨分片扫描。
- 唯一索引避免重复收藏。
- 收藏数量按收藏夹批量统计，不在页面逐条查询。
- 收藏成功后只更新当前卡片状态，不刷新整个列表。
