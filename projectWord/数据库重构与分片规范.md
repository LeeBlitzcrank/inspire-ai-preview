# 数据库重构与分片规范

## 目标

- 所有写路径按热点维度单分片命中。
- 所有列表路径可分页，禁止一次拉全量。
- 禁止 N+1 查询。
- 迁移可重复、可检查、可回滚思路明确。

## 新分片规则

| 数据 | 表 | 路由键 |
| --- | --- | --- |
| 收藏记录 | `collect_0 ~ collect_9` | `user_id % 10` |
| 点赞记录 | `user_like_0 ~ user_like_9` | `user_id % 10` |
| 评论 | `inspire_comment_0 ~ inspire_comment_9` | `inspire_id % 10` |

重要：

- 点赞按 `user_id` 分片，列表页判断“当前用户点赞了哪些灵感”只查一个分片。
- 评论按 `inspire_id` 分片，详情页评论分页只查一个分片。
- 评论表保留 `username/avatar` 冗余字段，列表查询不再逐条查用户表。

## 会话关系

新增：

```txt
conversation_member(
  id,
  conversation_id,
  user_id,
  unread_count,
  last_time,
  create_time,
  update_time
)
```

访问路径：

- `GET /message/conversations`：按 `conversation_member.user_id + last_time` 查会话，联表 message_conversation 和 user 一次性取对方资料。
- `GET /message/unread`：按 `user_id` 聚合未读数。
- `POST /message/read`：只更新当前用户在 conversation_member 中的未读计数。
- 查看消息前校验用户是否真的属于该会话。

旧 `message_conversation.user1_id/user2_id` 仍保留用于唯一 pair 约束，但不再作为会话列表的主查询入口。

## 分页

收藏夹内容接口：

```txt
GET /api/inspire/collect/list?folderId=...&page=1&size=20
```

返回：

```json
{
  "records": [],
  "total": 0
}
```

前端个人页和收藏夹页首屏只取 20 条，滚动或点击继续加载。

评论接口继续使用：

```txt
GET /api/inspire/{id}/comments?page=1&size=20
```

## 全量重建机制

本次不再迁移旧数据。

`docker/init/init.sql` 是唯一的全新数据库基线，包含：

- 新点赞分表 `user_like_0 ~ user_like_9`
- 新评论分表 `inspire_comment_0 ~ inspire_comment_9`
- `conversation_member` 会话关系表
- 所有高频查询联合索引

`reset-data.sh` 清库后由种子生成器直接按新结构写入，保证演示数据从第一天就符合新分片规则。

## 索引约束

- `collect_N(user_id, folder_id, create_time)`
- `user_like_N(user_id, inspire_id)` 唯一
- `inspire_comment_N(inspire_id, deleted, create_time)`
- `inspire_main(user_id, status, deleted, create_time)`
- `inspire_main(status, deleted, create_time)`
- `inspire_main(status, deleted, heat)`
- `user_follow(follower_id, create_time)`
- `user_follow(followee_id, create_time)`
- `conversation_member(user_id, last_time)`

## 种子数据

种子生成必须同步新结构：

- 点赞写入 `user_like_{user_id % 10}`
- 评论写入 `inspire_comment_{inspire_id % 10}`
- 会话同时写 `message_conversation` 和 `conversation_member`
- 收藏继续写入 `collect_{user_id % 10}`
- 灵感必须读取 `sys_category`，写入 `category_id`（一级）和 `sub_category_id`（二级）
- 标题、正文和展示 tag 都由同一条分类链路生成，不再维护一套独立硬编码分类
