## 二、压测发现的问题

### 1. 网关存在固定代理开销

优化前直接访问核心和搜索服务，与经过网关对比：

| 路径 | RPS | P95 |
| --- | ---: | ---: |
| 公开列表直连 Core | 420.29 | 480ms |
| 公开列表经过 Gateway | 314.24 | 537ms |
| 搜索直连 Search | 388.97 | 428ms |
| 搜索经过 Gateway | 217.85 | 953ms |

结论：

- 网关导致列表吞吐下降约 25%。
- 网关导致搜索吞吐下降约 44%。
- 搜索 P95 从 428ms 增加到 953ms。

### 2. 开发日志和 SQL 输出过多

问题：

- 网关鉴权过滤器在每个请求上输出 DEBUG 日志。
- 搜索服务每个搜索请求输出 INFO 日志。
- 核心服务个人页路径输出 `[PAGEDBG]` INFO 日志。
- MyBatis 使用 `StdOutImpl`，高并发时持续输出 SQL。

影响：

- 增加 CPU 占用。
- 增加磁盘和标准输出锁竞争。
- 干扰真实性能数据。

### 3. 公开只读接口仍走 Redis 限流器

问题：

- 网关默认过滤器对全部请求执行 Redis 令牌桶。
- 公开列表和公开搜索是只读接口，仍会为每次请求增加一次 Redis 远程调用。

影响：

- 增加网关 CPU。
- 增加 Redis QPS。
- 增加公开接口固定延迟。

### 4. 搜索没有结果缓存

问题：

- 相同关键词、分类和分页重复请求时，每次都访问搜索服务并查询 ES。
- 热门关键词会重复消耗 ES CPU。

优化前搜索在 100 并发下：

```text
217.85 RPS
P95 953ms
最大 1416ms
```

### 5. ES 查询没有充分利用过滤和字段裁剪

问题：

- 查询没有明确过滤 `status=1`。
- 查询没有明确过滤 `deleted=0`。
- 返回全部 `_source` 字段。
- 没有关闭不需要的 total 统计。
- `searchAfter` 参数存在，但后端没有使用。

### 6. 个人页收藏和点赞状态分开查库

问题：

- 收藏状态查询一次。
- 点赞状态查询一次。
- 两表都按同一个 `user_id` 分片，本可以合并。

影响：

- 个人页和收藏夹列表每次多一次数据库往返。

### 7. 评论表缺少 parent_id 联合索引

问题：

- 主评论查询带 `parent_id=0`。
- 回复查询带 `parent_id IN (...)`。
- 原有热门索引没有包含 `parent_id`。

当前数据量下仍能返回，但评论量继续增长后会增加扫描成本。

## 三、已实施的优化

### 1. 日志级别调整

默认日志：

```text
com.inspire=info
```

MyBatis：

```text
org.apache.ibatis.logging.nologging.NoLoggingImpl
```

保留环境变量：

```text
INSPIRE_LOG_LEVEL
MYBATIS_LOG_IMPL
```

需要排查 SQL 时再临时打开，不默认输出。

### 2. 移除公开只读接口的 Redis 限流

网关策略调整为：

- 登录接口：保留 Redis 限流。
- AI 接口：保留 Redis 限流。
- 公开只读列表和搜索：不再经过网关 Redis 令牌桶。
- 公开只读流量后续由 Cloudflare/WAF 或边缘层限流。

### 3. 搜索 Redis 缓存

缓存键：

```text
search:v1:{keyword}:{tag}:{page}:{size}:{searchAfter}
```

默认 TTL：

```text
30 秒
```

可通过以下配置调整：

```text
inspire.search.cache-ttl-seconds
```

缓存失败不影响搜索，自动回退到 ES/MySQL。

### 4. ES 查询优化

已增加：

- `status=1` 过滤。
- `deleted=0` 过滤。
- 分类过滤。
- `_source` 字段白名单。
- `track_total_hits=false`。
- `heat desc + id asc` 稳定排序。
- 支持传入 `search_after` 游标。

核心同步文档新增 `status` 字段，确保过滤条件有效。

### 5. 个人页关系状态合并查询

收藏和点赞改为一次 `UNION ALL`：

```sql
SELECT 'collect' AS kind, inspire_id
FROM collect_{shard}
WHERE user_id = ? AND inspire_id IN (...)

UNION ALL

SELECT 'like' AS kind, inspire_id
FROM user_like_{shard}
WHERE user_id = ? AND inspire_id IN (...)
```

减少一次数据库往返。

### 6. 评论联合索引

新增：

```sql
KEY idx_inspire_parent_hot
  (inspire_id, parent_id, deleted, like_count, create_time)

KEY idx_inspire_parent_time
  (inspire_id, parent_id, deleted, create_time)
```

已同步更新：

- `docker/init/init.sql`
- 本地 `inspire_comment_0 ~ inspire_comment_9`

## 六、当前剩余问题

### 1. 搜索冷缓存仍然较慢

首次搜索约 2 秒。

后续优化：

- 热门词主动预热。
- ES 查询进一步下推。
- 按关键词维度预生成热门搜索结果。
- 对超过 1 秒的查询记录慢日志。

### 2. 深分页仍然使用 from + size

`search_after` 后端已支持，但前端还没有使用游标。

后续优化：

- 搜索接口返回 `nextSearchAfter`。
- 前端滚动加载改用 `search_after`。
- 禁止超大 page 值。

### 3. 评论仍然一次返回主评论下全部回复

当前 20 条主评论可能返回较多回复。

后续优化：

- 主评论先返回 `replyCount`。
- 默认只带最新 3 条回复。
- 展开后调用独立回复分页接口。

### 4. 个人页仍然存在 count 查询

后续优化：

- 无限滚动改为 keyset 分页。
- 首屏返回 `nextCursor`。
- 总数改为低频缓存或近似值。

### 5. ES 仍然是定时全量同步

当前每 5 分钟对全部灵感执行批量同步。

后续优化：

- 发布、更新、删除事件通过 MQ 单条同步。
- 定时任务只做增量补偿。
- 全量重建改为单独管理命令。

## 八、当前结论

本轮优化主要解决了三个根因：

1. 高并发下无效日志和 SQL 输出。
2. 公开只读请求经过网关 Redis 限流的固定开销。
3. 搜索重复请求没有缓存，且 ES 查询没有裁剪。

当前本地万级数据下：

- 公开列表 100 并发 P95 已降到 309ms。
- 搜索缓存命中 100 并发 P95 已降到 338ms。
- 个人页 50 并发 P95 已降到 319ms。
- 评论 50 并发 P95 已降到 388ms。
- 所有回归测试均为 0 失败。

本轮优化已经达到当前阶段的性能目标。

## 九、本机测试能力边界

当前机器：

```text
型号：MacBookPro16,1
CPU：Intel Core i7-9750H
CPU 核心：12
物理内存：64GB
Docker CPU：12
Docker 可用内存：约 8.3GB
可用磁盘：约 61GB
```

需要注意：

- 主机有 64GB 内存，但当前 Docker Desktop 只分配了约 8GB。
- 核心、网关、MySQL、Redis、Elasticsearch、RocketMQ、MinIO 都运行在同一台机器。
- ApacheBench 也在同一台机器运行，并且压测流量经过 macOS Docker 端口转发。
- 单节点 ES、单节点 MySQL 和所有 Java 服务共享同一组 CPU 与磁盘。

因此当前结果反映的是：

```text
单机 Docker 全栈的固定瓶颈
```

不是：

```text
MySQL/ES 在万级数据量下的真实上限
```

## 十、可测试规模建议

### 1 万级

当前环境可以直接测试。

适合：

- 功能回归。
- 分页和索引验证。
- 查询正确性。
- P95 基线。

### 10 万级

在当前环境可以测试，但需要：

- 使用批量 SQL/JDBC 导入。
- 停止全量 ES 周期同步。
- 将 Docker 内存提高到 16GB 以上。

### 100 万级

需要：

- Docker 内存至少 24GB～32GB。
- 使用 `LOAD DATA LOCAL INFILE` 或专用批量生成器。
- ES 批量索引使用 bulk，而不是逐条调用业务接口。
- 压测客户端从 Docker 外部运行，最好使用 k6、wrk2 或多机压测。
- 将 MySQL、ES 与业务服务分开观察资源。

### 1,000 万级

单机可以尝试，但不适合作为常规全栈测试：

- 需要至少 32GB Docker 内存。
- 需要外置或更大的 NVMe 磁盘。
- 需要允许数小时的数据导入和索引构建。
- 需要关闭日志、关闭非必要服务、限制 JVM 堆。
- 需要分区、批量导入和分阶段验证。

### 1 亿级

当前笔记本和 61GB 可用磁盘不适合做亿级全栈压测。

亿级需要：

- 独立 MySQL 集群或分库分表集群。
- 多节点 Elasticsearch。
- 独立 Redis 集群。
- 独立压测机或多台压测客户端。
- 独立网络环境和监控系统。

## 十一、P1 完成项

### 1. 个人页 keyset 分页

已新增游标参数并兼容旧 page 接口。

当前逻辑：

```text
首屏：COUNT(*) + LIMIT 21
后续：WHERE create_time/id < cursor LIMIT 21
```

接口返回：

```text
nextCursor
hasMore
```

收益：

- 去掉每页 count 查询。
- 避免深分页 offset 扫描。
- `user003` 游标页 50 并发达到 `423.54 RPS`、P95 `182ms`。

### 2. 评论回复懒加载

当前主评论页只返回每个主评论最新的 3 条回复预览。

并新增：

- 主评论先返回 `replyCount`。
- 独立回复分页接口：

```text
GET /api/inspire/{id}/comments/{parentId}/replies
```

- 展开后调用回复分页接口。

收益：

- 第一页响应体更小。
- 避免单个高回复评论拖大整页。

### 3. 评论总数缓存

评论总数和回复总数按 Redis 缓存 30 秒，发布评论后主动失效。

收益：

- 去掉每次评论请求的 root count 查询。

### 4. 搜索 search_after 前端接入

后端和前端都已支持。

搜索页“加载更多”会传递：

```text
searchAfter={heat}_{id}
```

并具备：

- 后端查询使用 search_after。
- 搜索结果 Redis 缓存。
- page 参数仅保留首次搜索兼容。

## 十三、正确的大数据压测方式

不要再通过业务 HTTP 接口逐条生成千万级数据。

正确顺序：

1. 批量生成结构化数据。
2. 使用数据库原生批量导入。
3. 使用 ES bulk 构建索引。
4. 预热缓存。
5. 使用独立压测客户端。
6. 分接口单独压测。
7. 记录 P50/P95/P99、错误率、CPU、内存、磁盘和连接数。
8. 逐步扩大数据量和并发，不直接跳到极限。

## 十五、补充问题修复

### 1. 评论回复显示“继续显示 1/2”

现象：

- 实际只看到一条回复。
- 评论下方出现“继续显示 1/2 收起回复”。

根因：

- 主评论预览数量和真实 `replyCount` 在展开前可能短暂不一致。
- 前端只有用户点击“继续显示”时才加载剩余回复。

修复：

- 后端主评论第一页返回 `replyCount` 和最新 3 条回复预览。
- 新增独立回复分页接口：

```text
GET /api/inspire/{id}/comments/{parentId}/replies
```

- 前端点击“展开回复”时，如果已加载数小于真实回复数，自动加载剩余回复。
- 自动加载完成后使用接口真实 `total` 校正 `replyCount`。
- 如果真实回复数小于等于当前显示数，只保留“收起回复”。

验证：

```text
主评论：100000000000704281
真实回复数：10
接口 total：10
接口 count：10
```

零回复场景验证：

```text
主评论：100000000000704292
回复前：replyCount=0
回复后：replyCount=1
接口返回回复：1 条
```

测试回复已在验证后删除。

进一步定位：

- 旧前端在提交回复后会先做一次本地乐观插入。
- 如果浏览器内存里还保留上一次测试的回复，就会和服务端真实回复同时存在。
- 因此会出现 `replyCount` 和当前渲染回复数不一致，显示“继续显示 1/2”。

最终修复：

- 回复成功后不再保留本地乐观记录。
- 立即重新请求当前评论第一页。
- 使用服务端返回的 `replyCount` 和回复记录重新渲染。
- 如果新回复不在预览中，再调用独立回复分页接口补齐。
- 页面刷新后不会残留幽灵回复。

### 2. 生产创建灵感上传图片和视频报错

根因分为两部分：

1. 前端所有请求共用 15 秒超时，图片压缩上传和视频上传很容易超时。
2. 视频 MIME 校验只接受严格视频 MIME，部分浏览器和客户端会发送：

```text
application/octet-stream
```

即使扩展名和文件魔数都是合法 MP4，也会被错误拒绝。

修复：

- 上传请求单独使用 180 秒超时。
- 设置：

```text
maxBodyLength=Infinity
maxContentLength=Infinity
```

- 允许 `application/octet-stream` 进入视频扩展名和魔数校验。
- Gateway WebFlux 内存缓冲设置为 16MB。
- 上传失败时优先展示后端真实错误信息。

本地验证：

| 文件 | 大小 | 结果 | 耗时 |
| --- | ---: | --- | ---: |
| JPG 图片 | 205KB | 200，生成 200/400/800 WebP | 0.93s |
| MP4 视频 | 22MB | 200，生成视频封面 | 1.02s |

视频返回：

```json
{
  "url": "/uploads/{filename}.mp4",
  "type": "video",
  "duration": "18",
  "thumbUrl": "/uploads/thumb_{filename}.mp4.jpg"
}
```

生产环境还需要确认：

- Cloudflare 当前套餐允许的请求体上限。
- Cloudflare 上传路径没有被 WAF 拦截。
- 生产网关没有额外 15 秒代理超时。

### 3. 视频上传一直停在 99%

根因：

- 前端原来强制把上传进度限制在最多 99%。
- 文件字节上传完成后，后端仍在同步执行：

```text
ffmpeg 截取首帧
ffprobe 读取视频时长
```

- 如果 ffmpeg 处理较慢，前端会一直显示 99%，看起来像卡死。
- 原 ffmpeg 和 ffprobe 调用没有超时，异常视频可能长时间阻塞。

修复：

- 文件字节上传到 100% 后，任务状态切换为：

```text
服务器处理中...
```

- 前端不再把进度锁死在 99%。
- ffmpeg 封面生成增加 45 秒超时。
- ffprobe 时长读取增加 5 秒超时。
- 超时后跳过封面或时长，不影响视频文件本身上传成功。
- 重试时状态重新回到上传中。

验证：

```text
文件：22MB MP4
HTTP：200
时长：18 秒
封面：成功
耗时：2.37 秒
```
