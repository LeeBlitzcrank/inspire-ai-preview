# 大数据压测数据生成说明

> 更新时间：2026-09-23
> 适用范围：本地性能测试、长列表测试、分页测试、ES 搜索测试、消息和互动压测
> 默认状态：不开启，只有显式设置 `INSPIRE_DEMO_SCALE=large` 才生成

> 压测问题、优化过程和优化前后对比见：
> `projectWord/性能压测问题与优化报告.md`

## 一、模式说明

演示数据分为两档：

| 档位 | 环境变量 | 用途 |
| --- | --- | --- |
| small | `INSPIRE_DEMO_SCALE=small` | 默认演示数据，启动快 |
| large | `INSPIRE_DEMO_SCALE=large` | 万级压测数据，启动较慢 |

大数据模式不会替换原有小数据模式，只会在启动时额外运行：

```text
backend/inspire-core/src/main/java/com/inspire/platform/core/seed/LargeDataSeeder.java
```

小数据种子仍是：

```text
backend/inspire-core/src/main/java/com/inspire/platform/core/seed/DemoDataSeeder.java
```

两个生成器都有顺序和幂等控制：

```text
DemoDataSeeder  -> Order(1)
LargeDataSeeder -> Order(2)
```

## 三、数据关系

大数据不是孤立表数据，生成时保持以下关系：

- 灵感引用真实 `sys_category` 两级分类。
- 点赞、收藏按 `user_id % 10` 写入分表。
- 评论按 `inspire_id % 10` 写入分表。
- 评论点赞按 `user_id % 10` 写入分表。
- 收藏记录关联真实收藏夹。
- 私信同时生成会话、会话成员和消息。
- 通知关联真实用户和灵感。
- AI 历史关联压测用户。
- 灵感完成后自动同步 Elasticsearch。

## 七、幂等规则

`LargeDataSeeder` 启动时检查压测用户数量：

- 已有 10,000 个压测用户：直接跳过。
- 有部分压测用户：认为上次可能中断，跳过并输出警告。
- 没有压测用户：开始生成。

部分失败后的推荐处理方式：

```bash
INSPIRE_DEMO_SCALE=large ./reset-data.sh
```

不要在部分生成后直接反复启动，否则可能产生难以识别的重复关系。

### 网关限流说明

网关默认限流：

```text
普通接口：50 req/s
突发容量：100
AI 接口：5 req/s
突发容量：10
```

因此测试中出现下面结果时，不是系统崩溃：

```text
150 次 HTTP 200
50 次 HTTP 429
```

原因是 200 次请求在很短时间内共用了同一个 IP 令牌桶。

低并发基线应在限流容量内单独执行，不要把列表、搜索、个人页测试并行运行，否则它们会共享同一个限流桶，结果会互相干扰。

### 当前低并发基线

每组测试：

```text
80 次请求
10 并发
```

结果：

| --- | ---: | ---: | ---: | ---: |
| 公开列表 | 80/80 | 188.53 | 53.04ms | 98ms |
| 搜索 | 80/80 | 186.73 | 53.55ms | 74ms |
| 登录后个人页 | 80/80 | 125.47 | 79.70ms | 111ms |
| 评论第一页 | 80/80 | 71.66 | 139.55ms | 181ms |

所有低并发测试：

### 高并发梯度结果

公开列表：

| 请求数 | 并发 | RPS | P50 | P95 | P99 | 最大 | 失败 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 20 | 273.00 | 69ms | 110ms | 136ms | 264ms | 0 |
| 2,000 | 50 | 301.80 | 162ms | 268ms | 397ms | 461ms | 0 |
| 3,000 | 100 | 314.24 | 333ms | 537ms | 661ms | 721ms | 0 |

公开列表观察：

- 并发从 20 提升到 100 后，RPS 只从 273 提升到 314。
- 吞吐已经进入平台期。
- P95 从 110ms 上升到 537ms。
- 系统没有错误，主要问题是排队延迟增加。

搜索：

关键词：

```text
计划
```

| 请求数 | 并发 | RPS | P50 | P95 | P99 | 最大 | 失败 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1,000 | 20 | 156.12 | 113ms | 244ms | 284ms | 346ms | 0 |
| 2,000 | 50 | 196.19 | 244ms | 479ms | 575ms | 650ms | 0 |
| 3,000 | 100 | 217.85 | 416ms | 953ms | 1,162ms | 1,416ms | 0 |

搜索观察：

- 100 并发时 P95 达到 953ms。
- 搜索链路已经成为目前最明显的尾延迟来源。
- 压测过程中：
  - `inspire-gateway` CPU 约 279%
  - `inspire-search` CPU 约 265%
  - `inspire-es` CPU 约 241%
- 搜索优化应优先检查 ES 查询、结果转换和网关到搜索服务的调用链。

### 当前瓶颈判断

1. 所有高并发测试都是 0 失败，没有服务崩溃。
2. 网关提高限流后，429 已消失。
3. 公开列表最平稳，但 100 并发后吞吐进入平台期。
4. 搜索最重，100 并发时 P95 接近 1 秒。
5. 个人页和评论在 50 并发时 P95 已超过 500ms。
6. 下一步优化方向应优先放在：
   - 搜索接口查询与响应转换。
   - 评论分页返回的数据体积。
   - 个人页接口的重复查询和缓存命中。
   - 网关与下游服务的连接复用和线程模型。

### 网关开销对比

为了确认是网关还是下游服务，分别绕过网关直接压测：

公开列表：

| 路径 | RPS | P95 | P99 | 最大 |
| --- | ---: | ---: | ---: | ---: |
| Gateway `8080` | 314.24 | 537ms | 661ms | 721ms |
| Core `8083` | 420.29 | 480ms | 629ms | 954ms |

搜索：

| 路径 | RPS | P95 | P99 | 最大 |
| --- | ---: | ---: | ---: | ---: |
| Gateway `8080` | 217.85 | 953ms | 1,162ms | 1,416ms |
| Search `8086` | 388.97 | 428ms | 501ms | 587ms |

结论：

- 公开列表经过网关后吞吐下降约 25%。
- 搜索经过网关后吞吐下降约 44%。
- 搜索经过网关后 P95 从 428ms 增加到 953ms。
- 网关是当前第一优先级优化点。

优先检查：

- 开发环境 DEBUG 日志。
- Redis 限流器每次请求的远程调用。
- 路由转发连接池。
- 每个请求的鉴权日志和响应头处理。

### 2. 数据库数量和关联正确性

测试重点不是只看主表，而是检查所有分表和关系表。

检查核心数量：

```sql
SELECT COUNT(*) FROM `user` WHERE username LIKE 'perf%';
SELECT COUNT(*) FROM inspire_main WHERE id >= 410000000000000000;
SELECT COUNT(*) FROM collect_folder WHERE id >= 420000000000000000;
```

检查分表：

```sql
SELECT
  (SELECT COUNT(*) FROM user_like_0)
  + (SELECT COUNT(*) FROM user_like_1)
  + (SELECT COUNT(*) FROM user_like_2)
  + (SELECT COUNT(*) FROM user_like_3)
  + (SELECT COUNT(*) FROM user_like_4)
  + (SELECT COUNT(*) FROM user_like_5)
  + (SELECT COUNT(*) FROM user_like_6)
  + (SELECT COUNT(*) FROM user_like_7)
  + (SELECT COUNT(*) FROM user_like_8)
  + (SELECT COUNT(*) FROM user_like_9) AS like_total;
```

评论表同理检查 `inspire_comment_0 ~ inspire_comment_9`。

重点验证：

- 点赞记录没有重复的 `user_id + inspire_id`。
- 收藏记录没有重复的 `user_id + inspire_id`。
- 评论的 `inspire_id` 都能在 `inspire_main` 找到。
- 回复的 `parent_id` 指向同一灵感下的主评论。
- 会话存在对应的 `conversation_member`。
- 消息的 `conversation_id` 都存在。

## 十、注意事项

- 大数据模式只用于本地或独立压测环境，不建议直接部署到生产。
- 生成前确认本机磁盘空间充足。
- 生成完成后首次搜索或后台用户列表可能触发索引和数据预热。
- 若要测试移动端大量数据，建议使用 `user001` 或 `perf00001` 登录。
- 如果要恢复干净的小数据环境，执行默认 `./reset-data.sh`。
